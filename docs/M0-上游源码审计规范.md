# M0 - 上游源码审计规范

> M0 的目标不是选边站，而是回答：
>
> **A-Share Research OS 的每一层应该采用、适配或参考哪个成熟实现。**
>
> TideTrading 是优先审计对象，不是预设结论。

---

## 1. 审计对象

```text
TideTrading        首选主工程候选（A 股/港股、Python、FastAPI、React/Vite/TS、多 Agent、SSE、Docker）
OpenAlpha CN       Evidence/PIT 参考重点
觀瀾 (financial-analyst)   UI/UX 第一参考重点
Qlib               专业 QuantEngine（按需接入）
RD-Agent           后期可选（Hypothesis → Experiment → Evaluation → Feedback）
TradingAgents      可选 ResearchEngine（分析师/辩论能力）
```

上游仓库必须位于正式仓库之外（`upstreams/`），禁止整体并入正式仓库。

---

## 2. 审计深度要求

不得只读 README。每个候选必须：

1. 记录 repository URL、default branch、HEAD commit、最后提交时间；
2. 检查 LICENSE（类型 + 文件级许可风险）；
3. 遍历目录结构，定位关键源码：
   - 数据层（data loader / provider / registry / fallback）
   - Agent / 编排层
   - API 层（FastAPI / routes）
   - 前端（framework / i18n / theme 基础）
   - Quant / backtest 能力
   - 调度 / worker / 任务机制
   - 配置与部署（Docker / env）
4. 实际运行（至少 backend 启动、CLI、或 import 级验证，按项目形态适配）；
5. 运行该项目已有测试（或记录为何无法运行）；
6. 评估维护活跃度（最近提交、issue/PR 情况、代码质量）；
7. 给出结论：`ADOPT / ADAPT / REFERENCE_ONLY / REJECT` + 理由。

---

## 3. 评估矩阵维度

每个候选按以下维度打分（0–5）并记录证据：

```text
a-share-data-coverage     A 股数据覆盖与真实可用性
engineering-completeness  工程完整度（API/前端/部署/配置）
maintainability           代码质量、结构、可维护性
license                   许可证与复用友好度
tests                     测试覆盖与可运行性
backend-api               后端与 API 成熟度
frontend                  前端成熟度
i18n                      双语基础
theme                     主题基础
agent-orchestration       Agent 编排能力
quant-backtest            量化/回测能力
pit                       Point-in-Time 能力
evidence-provenance       证据溯源能力
task-scheduling           任务调度能力
deployment                部署成熟度
migration-cost            迁移/改造成本（低=好）
```

---

## 4. 采用等级定义

```text
ADOPT            成熟能力直接作为正式系统一部分，经稳定边界接入 Research Core
ADAPT            能力有价值，但必须包装/裁剪/重构后使用
REFERENCE_ONLY   只借鉴设计/算法/UI/数据模型/工程思想，不形成运行时依赖
REJECT           当前不采用，记录理由
```

允许不同层分别选择不同最优实现，不要求一个项目解决全部问题。
