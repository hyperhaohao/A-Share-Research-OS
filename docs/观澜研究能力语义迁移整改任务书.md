## 一、整改背景

当前 A-Share Research OS 已具备 Evidence、PIT Snapshot、Claim、Thesis、Artifact、Research Memory、Experience Card、Workflow、Screening、Strategy、Monitor 等工程基础，以及相应 API 和部分 UI。

但本轮复审确认，大量迁移仍停留在：

    页面 + 对象 + 接口 + 状态记录

尚未完整达到：

    研究方法 + 研究语义 + 可执行规则 + 验证监控复盘闭环

必须纠正以下错误判断：

- 产业分类层级不能等同于产业链。
- Driver、Narrative、Transmission 对象存在，不能等同于产业研究闭环完成。
- Experience Card 能创建，不能等同于“原—炼—验—用”完成。
- DAG 能连线，不能等同于工作流已经传递真实数据。
- 从经验卡启动 Screening，不能等同于经验方法生成了选股规则。
- 计算未来收益，不能等同于执行了策略条件回测。
- 监测行情和新闻，不能等同于监控某个策略。
- 创建新版本记录，不能等同于 Replay 因果反馈链成立。
- 后端返回临时字典，不能等同于研究产品已经产品化。

本轮整改不以继续扩充页面数量为目标，而是修复观澜研究能力的语义真实性、可执行性、可验证性、可追溯性和产品闭环。

## 三、整改总原则

### 3.1 研究语义优先

每个模块必须回答：

1. 输入的研究对象是什么？
2. 执行的研究方法或规则是什么？
3. 输出的研究结论是什么？
4. 哪些 Evidence 支撑或反对？
5. 结论在什么 PIT 时间有效？
6. 谁或什么流程改变了结论？
7. 如何验证、监控和复盘？

只能证明页面打开、API 返回 200 或数据库产生记录，不得标记研究能力 PASS。

### 3.2 保留正确基础设施

不得无理由重建已经稳定的 Evidence、Source Trust、PIT Snapshot、Claim、Thesis、Artifact、Provenance、Confirmation Gate、Audit Event 和 Run/Event/Metric 基础结构。整改重点是让观澜研究功能真正消费它们。

### 3.3 生产规则由后端掌握

产业链关系、选股规则、策略入场/退出/风险规则、监控条件、信号等级和 Trust Gate 不得由客户端临时拼装。客户端可创建草稿，但正式执行必须引用后端版本化 Definition。

### 3.4 PIT 与 Provenance 是强约束

所有研究产物至少包含：

- artifact_id、artifact_type、version
- as_of_time、snapshot_id
- instrument_ids / industry_ids
- input_artifact_ids、evidence_ids
- created_by、created_at

Artifact 注册失败时不得吞异常后继续宣称成功。

### 3.5 Definition、Run、Result 分离

    Definition Version
          ↓
    Run with PIT Inputs
          ↓
    Immutable Result
          ↓
    Artifact + Provenance

UI 描述字段不得冒充可执行规则。

## 四、禁止假通过规则

以下任一情况出现，对应功能只能判定 PARTIAL 或 FAIL：

1. 测试遇到 404 后直接 return。
2. Golden 手工插入结果，绕过生产 API。
3. 只检查对象存在，不检查研究语义。
4. 固定收益统计冒充策略回测。
5. Experience Card 只作来源标签，不生成规则。
6. Workflow Edge 不传数据，却标记数据流 DAG。
7. Artifact 注册失败被 `except Exception: pass` 吞掉。
8. 使用硬编码公司、行业、股票或 Golden 特例。
9. 同源转载或同一 Evidence 派生的多个 Signal 被当成独立佐证。
10. 文档或 Commit 声称 PASS，但代码和测试未实现。
11. 前端入口指向不存在路由，却标记产品化完成。
12. 临时返回字典无 Artifact/PIT/Version/UI，却标记 Research Product PASS。
13. daemon thread 执行重要长任务，却无恢复、取消和失败状态。
14. 只改描述文字，不改可执行规则，却标记策略完成学习。

## G4：Typed Dataflow Workflow

每个 Node Definition 必须声明 input_ports、output_ports、input_schema、output_schema、parameters_schema、execution_policy；Edge 必须声明 source_port、target_port 和 data_contract。

必须实现：

1. 为每个节点保存不可变 NodeInput、NodeOutput、NodeEvent 和 Artifact。
2. 禁止节点绕过上游输出读取共享 metrics，除非明确声明外部依赖。
3. 支持分支、合并、失败传播、重试、取消、暂停、恢复。
4. Output Node 消费节点参数或上游输入，不得忽略 UI 的 card_id。
5. Definition Run 具有真实 instrument/industry scope。
6. 校验孤立节点、不可达节点、端口类型、必填输入和重复输出。
7. UI 展示节点输入输出、执行状态、失败重试和 Run Replay。

最低节点类型：Evidence、Quote、Industry、Transform、Filter、Rule、Screening、Backtest、Validation、Prediction、Thesis Impact、Experience Output、Memory Output、Notification、Human Confirmation。

DoD：

- 双分支数据互不覆盖。
- 下游输入与指定上游输出一致。
- 端口类型不匹配时不能发布。
- 中断后可从最近完成节点恢复。

## G6：Executable Strategy Lab

建立：

    ScreenDefinition + Experience Components
                  ↓
    StrategyDefinition Vn
                  ↓
    PIT Backtest
                  ↓
    Orders / Positions / Trades / NAV / Metrics

StrategyDefinition 至少包含 universe_rule、entry_rules、exit_rules、position_sizing、risk_rules、rebalance_policy、benchmark、cost、slippage、data_requirements、source artifacts。

必须实现：

1. Entry、Exit、Position、Risk 均为可执行规则。
2. 只在 Entry 触发时建立仓位。
3. Exit 和 Risk 真实改变交易路径。
4. 支持交易成本、滑点、停牌、涨跌停、退市和缺失数据。
5. 禁止重叠未来收益窗口冒充独立样本。
6. 提供 benchmark、excess return、drawdown、turnover、exposure、sample size。
7. 分离 In-sample、Validation、Out-of-sample。
8. Regime 有明确可复现定义，不能简单按年份命名。
9. Validation 设置样本、稳定性、风险和 OOS 门槛。
10. Backtest 可重放并注册 Artifact。

DoD：

- 修改 Entry 后，交易日期和收益发生可解释变化。
- 修改 Exit/Risk 后，持仓、回撤和收益发生变化。

## G8：Causal Replay

严格建立：

    MonitorRun → Observation → Signal → Decision
    → Prediction → Outcome → Attribution
    → Experience Revision → Screen/Strategy Revision

必须实现：

1. Prediction 直接引用 Decision 或其 Signal/MonitorRun。

3. Attribution 区分 thesis_error、evidence_error、timing_error、rule_error、execution_error、regime_change、insufficient_data。

- rule_error 反馈能改变 Strategy Rule，并使新旧回测不同。
